# PatchHive v0.3.0 scanner intake benchmark

This report records the local evidence for
[issue #13](https://github.com/Yuki9814/PatchHive/issues/13). It measures the
supported 25, 100, and 250-finding boundary without making adoption or external
usability claims.

## Method

- Production Vite build served locally with network access disabled by the CSP.
- Deterministic agent-hygiene JSON and SARIF fixtures generated in memory.
- One warmup followed by five measured runs for each format and finding count.
- Timings include preview, import plus first-page render, severity filtering,
  one accepted-risk note plus local persistence, handoff download, and reload.
- Heap observations use Chromium's `JSHeapUsedSize` metric after reload.
- Values below are `p50 / p95`; times are milliseconds and memory is MiB.

Environment: macOS 27.0.0 (`arm64`), Apple M5 with 10 logical CPUs and 16 GiB
RAM, Node.js 22.22.3, Playwright Chromium 151.0.7922.34. The implementation
worktree was based on `ad1e57dc9366be24ab690a64e9d3bffc17d398d9`.

## Reproduce

```bash
npm ci
npx playwright install chromium
PATCHHIVE_BENCH_RUNS=5 npm run benchmark:scanner -- \
  --output /tmp/patchhive-scanner-benchmark.json
node scripts/generate-scan-fixtures.mjs \
  --output /tmp/patchhive-scanner-fixtures
```

The normal Chromium E2E suite imports the deterministic 250-finding SARIF
fixture, checks 25-item pagination and filtering, records an accepted-risk note,
reloads schema v7 state, and verifies that mismatched scan scopes remain
blocked. CI treats that as a functional smoke test; it does not enforce local
timing budgets on a shared runner.

## Limits

- The fixtures are synthetic and seeded; they do not represent repository
  prevalence or scanner accuracy.
- This is one headless Chromium environment, not a cross-browser performance
  claim.
- Heap figures are observations rather than leak proofs.
- External maintainer trial: **N=0, not started, not accepted**. No handoff
  completion rate, user feedback, adoption, or ecosystem impact is claimed.
